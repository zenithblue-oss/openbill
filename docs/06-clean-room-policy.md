# Clean-Room and Contribution Policy

OpenBill is an independent, clean-room project. This policy protects contributors, users,
and the project. It applies to everyone who submits code, documentation, assets, test data,
or designs.

## 1. What clean-room means here

Clean-room development separates **behavioral specifications** from **implementation**.

- You may study public product documentation, pricing pages, help-center articles, store
  listings, and user-visible behavior.
- You may record functional requirements, workflows, and interface behavior in your own
  words.
- You may not copy source code, decompiled code, resources, strings, database schemas, or
  assets from a proprietary application.
- The implementation must be written from the specification and from public accounting
  knowledge, not by translating someone else's code.

OpenBill's specifications live in this repository. They are written in original language
and contain no proprietary code.

## 2. Prohibited contributions

Do not submit:

- APK, AAB, XAPK, DEX, JAR, or native library files from another product.
- Decompiled Java, Kotlin, smali, or reconstructed source from another product.
- Extracted resources: icons, illustrations, themes, fonts, sounds, layouts, or string
  tables.
- Database schemas, migration files, or fixture data copied from another product.
- Scraped user data, private API responses, or credentials.
- Downloaded web application bundles, over-the-air frontend bundles, or any code or assets
  fetched from another product's servers.
- Private hostnames or endpoints, cloud project or app identifiers, crash-reporting
  tokens, API keys, IPC or message channel names, obfuscated class names, or verbatim
  user-interface strings from another product.
- Screenshots or recordings of another product used as design assets.
- Code generated by feeding another product's decompiled code into an AI tool.
- Code you do not have the right to license under Apache-2.0.

If you are unsure whether a file is allowed, do not commit it. Ask in an issue first.

## 3. Allowed references

You may reference:

- Public help-center articles and product documentation, summarized in your own words.
- Public pricing and feature pages.
- Public standards: GST law, HSN/SAC schedules, UPI specifications, PDF and CSV formats,
  Tally XML documentation, and Android platform documentation.
- Public open-source libraries with compatible licenses.
- Your own screenshots of your own implementation.
- User research conducted with informed consent and without confidential information.

When in doubt, prefer a public standard over a competitor's behavior.

## 4. Contribution provenance

Every pull request must include a provenance statement:

```text
Provenance:
- [ ] This contribution is original work.
- [ ] It contains no code, assets, strings, or data copied from a proprietary product.
- [ ] Any third-party code is compatible with Apache-2.0 and is attributed.
- [ ] Any test data is synthetic or properly licensed.
```

For substantial contributions, add a line to `CONTRIBUTORS.md` if one exists, or include
your name and the contribution scope in the pull request.

## 5. Reverse-engineering rules

Reverse engineering is allowed only where you have a lawful right to do it and only for
interoperability or research.

Do not:

- Bypass authentication, licensing, or technical protection measures.
- Access other users' data.
- Interfere with a production service.
- Extract secrets, signing keys, or private endpoints.
- Publish material that enables abuse of another product.
- Use another product's trademarks in OpenBill's name, package, icon, or marketing.

Do:

- Keep raw artifacts in a private workspace.
- Record observations as requirements, not as copied implementation.
- Cite class or feature names only when necessary to explain behavior; never publish
  obfuscated identifiers or internal channel, package, or module names.
- Redact personal data, tokens, and identifiers from any shared notes.
- Delete raw artifacts when they are no longer needed.

### Desktop installers and Electron applications

Desktop applications built on Electron or similar shells get extra care, because their
packages can carry configuration that points at live services.

- Obtain the installer only from the vendor's public download page. Do not use leaked, cracked,
  or account-gated builds.
- Unpacking the installer and reading its application archive and compiled shell code is
  allowed for interoperability research. Native binaries and the stock Electron runtime are out
  of scope.
- Do not fetch the over-the-air web frontend bundle, version documents, update feeds, or
  content delivery hosts that the shell contacts, and do not open private endpoints in a
  browser or script. The hosted web application is another product's server-side software.
- Do not launch the shell against the vendor's services, create or use accounts, or capture
  network traffic.
- Do not copy or publish endpoint addresses, update and CDN hostnames, cloud project or
  database identifiers, crash-reporting tokens, API keys, IPC or bridge channel names, window
  or preload implementation details, or verbatim strings. Describe behavior generically, for
  example "a cloud-hosted version document" or "a vendor CDN".
- Record the artifact hash, size, version, and date so the study is reproducible, and keep the
  artifact itself and its extracted files in a private workspace.
- Findings about weaknesses (for example, unsigned downloaded code) are recorded only as
  generic improvement requirements for OpenBill, never as a vulnerability report against
  another product.

## 6. Design and asset policy

- All icons, illustrations, and themes must be original or licensed for Apache-2.0
  distribution.
- Do not imitate another product's distinctive visual identity, mascot, or trade dress.
- Fonts must be licensed for embedding and redistribution.
- Sample invoices must use fictitious businesses and original layouts.
- Screenshots in documentation must show OpenBill, not another product.

## 7. Trademarks

"myBillBook", "Flobiz", and related names are trademarks of their respective owners.

OpenBill may use these names only for nominative comparison, such as "an alternative to
myBillBook" in documentation, provided the use is truthful and does not imply endorsement.
Do not use them in:

- The application name, package ID, or domain.
- The logo or icon.
- Advertisements or store listings that imply affiliation.
- Any statement that OpenBill is a fork, partnership, or official alternative.

The repository was formerly named `openbill-android` and is now `openbill`
(https://github.com/zenithblue-oss/openbill). The product name is
OpenBill.

## 8. Licensing

- Contributions are accepted under the Apache License 2.0.
- By submitting a pull request, you confirm you have the right to license your contribution
  under Apache-2.0.
- Do not add dependencies with copyleft licenses that would impose obligations on the
  combined work without prior discussion.
- Record third-party notices in `NOTICE` or a generated license report.

## 9. Review process

Reviewers should ask:

1. Is the behavior described in original words?
2. Is the implementation independent of any decompiled source?
3. Are assets and fixtures original or licensed?
4. Is the license compatible?
5. Does the contribution add a dependency that weakens privacy or security?

A reviewer may reject a contribution that cannot demonstrate provenance. Rejection is not
an accusation; it is a safeguard for the project.

## 10. Incident response

If proprietary material is accidentally committed:

1. Do not rewrite history alone. Notify the maintainers privately.
2. Remove the material from the working tree and from history as directed.
3. Invalidate any leaked secrets immediately.
4. Document the incident and the remediation without publishing sensitive details.
5. Review the contribution process to prevent recurrence.

If you believe OpenBill contains material that infringes your rights, contact the
maintainers with the specific file, the right you hold, and the requested action. The
project will review and remove or replace the material if warranted.

## 11. AI-assisted contributions

AI tools are allowed, but the same provenance rules apply.

- Do not paste decompiled code from another product into a model and submit the output.
- Review generated code for license and security issues.
- Test generated code as you would your own.
- Disclose substantial AI assistance in the pull request when it affects provenance.

## 12. Contributor checklist

Before opening a pull request:

- I read this policy.
- My code is original or compatibly licensed.
- I did not copy decompiled code, assets, strings, or schemas.
- My test data is synthetic.
- I added the provenance statement.
- I ran the relevant tests and lint.
- I did not include secrets or personal data.
- I did not include private endpoints, hostnames, project identifiers, or internal channel
  names from another product.
